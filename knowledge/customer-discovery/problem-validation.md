# Problem validation

A problem is worth solving when it is **real, frequent or severe, urgent, poorly served, and the person would act to fix it**. The skill assesses each dimension separately, because a problem can be real but trivial, or severe but rare.

| Dimension | Evidence that counts | Not enough on its own |
|---|---|---|
| Existence | Specific past incidents described unprompted | "Yes, that sounds like a problem" |
| Frequency | Dates and counts of recent occurrences ("every Sunday") | "It happens sometimes" |
| Severity | Cost in time or money; consequences described | Strong adjectives |
| Urgency | Active search for a solution; a deadline | Agreement that it would be nice to fix |
| Dissatisfaction with alternatives | Workarounds built; tools abandoned; complaints with specifics | "Current tools are fine, but…" |
| Demand for alternatives | Searching, asking peers, trialling competitors | Waitlist sign-ups alone |
| Behaviour change | Has already changed process or tools for this problem | Says they would switch |
| Purchase commitment | Payment, deposit, signed pilot, letter of intent with terms | Survey willingness to pay |

**Counting rule.** Report problem evidence as "*n* of *N* interviews in segment S described a specific recent incident", with the interview IDs. A single vivid quote is an example, not a pattern. Prompted agreement is recorded with polarity and a note that it was prompted, and is weighted below unprompted mentions.

**Disconfirming evidence is evidence.** Interviews where the problem is absent are recorded as negative mentions (`[problem:<theme> -]`). The analysis shows them beside the positive ones, so a theme mentioned by 6 people and denied by 9 is not mistaken for a strong finding.
